# Decisions

Choices made where the spec says **(decide)** or is silent, with short rationale. The spec (`02-v0-spec.md`) remains authoritative.

## Stack

- **TypeScript on Node ≥ 24, no build step.** Node runs `.ts` files natively (type stripping); `tsc --noEmit` is only used for type-checking. Developed and tested on Node 26.
- **Zero runtime dependencies.** `node:http` for the server, `node:sqlite` for storage, the global `URLPattern` for tool patterns. Dev-only: `typescript`, `@types/node`, `linkedom` (DOM for the UI smoke test). Less supply-chain risk, trivial self-hosting.
- **Frontend: vanilla ES modules** in `public/`, no framework, no bundler. Allows a strict CSP (`script-src 'self'`, no inline scripts or styles) and keeps the UI one replaceable view over the JSON API.
- **SQLite** behind one data-access module (`src/repo.ts`); nested values (criteria, records, settings) stored as JSON columns. Postgres stays possible by reimplementing `repo.ts`.
- **HTTP layer is a pure function** `route(request) → response` with a thin `node:http` wrapper, so it's testable without sockets.

## State mapping

- **GitHub PR**: draft → `not_started`; open → `open`; merged → `accepted`; closed unmerged → `rejected`.
- **GitHub issue**: closed `completed` → `accepted`, `not_planned` → `rejected`, `duplicate` → `withdrawn`, closed with no reason (old issues) → `concluded` (needs confirmation). An `/issues/N` URL that points to a PR is handled as a PR.
- **GitLab MR**: same as GitHub; `locked` → `open`.
- **GitLab issue**: closed → `concluded`, because GitLab doesn't record why it was closed, so the steward confirms. Moved → `withdrawn`.

## Spec "(decide)" items

- **One criterion per kind**: enforced strictly, as recommended.
- **URL pattern syntax**: WHATWG **URLPattern** (`https://pol.is/:id`, `https://forum.example.org/t/*`). It's easier to read and write than regexes for people proposing manual tools.
- **Evaluation interval**: every 15 min (`TICK_MS`), and also immediately after every refresh and every relevant action (adopt, criteria change, address, manual update…).
- **Refresh schedule**: open items every 15 min, terminal ones daily. On errors: exponential backoff (15 min × 2ⁿ, up to 24 h) that respects `Retry-After`/rate-limit reset. ETag conditional requests. Previews are cached for 60 s so paste-then-create fetches once. On-demand refresh is throttled to once per 30 s per process.
- **Addressing objections**: the window **pauses** at the first open objection. Once all are addressed, it resumes for the time that was left, or for a full window if fewer than 2 days were left.
- **Steward inactive**: no activity-log entry by the steward's display name anywhere in the space for 7 days. After that, anyone can confirm.
- **Link rotation**: CLI command `rotate-link <space-id> edit|view`, logged as `link.rotated` by `operator`.
- **Space creation**: CLI only (`create-space`), which prints both links once. No public creation page, so nobody can create spaces on a pilot server without the operator.
- **Atom feed**: included at `/feed/<token>.atom` (last 50 events). The UI only offers it with the view link, so the edit link doesn't end up in feed readers.
- **REST shape**: see `docs/API.md`.
- **CSP**: strict. `default-src 'self'`, no inline scripts or styles, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`.

## Where the spec was silent

- **Additive fields.** `ResolutionRecord.outcome` (the final `NormalizedState`) and `.attested`; `PendingResolution.suggested_outcome`; `Question.drop_reason`, `default_window`, `rules_payload`, `reopened_at`, `reopen_baseline_state`. All are additive and appear in the export.
- **Outcome on confirmation.** The confirmer picks the outcome, with a sensible default: the process state for `process_outcome`, the process state (if terminal) or `concluded` for `date`, and `accepted` for `default_rule` and `attested`. This covers "let the steward choose accepted/rejected" for Loomio.
- **Rules payloads apply only when the outcome is `accepted`.**
- **Third Rules template, `set_tool_enabled`.** §8 requires that disabling a tool goes through a Rules question; a template makes it apply automatically.
- **Rules proposals are immutable** once created, so nobody can change a proposal after others have stopped objecting. To change one, drop it and propose again.
- **Rules questions** must include the `default_rule` criterion (others may be added). They **don't count toward the active cap**, which is about the group's attention on main questions; capping them could block changes to the rules themselves.
- **Reopening.** A process outcome that already counted before reopening doesn't trigger again (the baseline state is stored), and a date that was already in the past at reopening is ignored. Otherwise a reopened question would resolve again within 15 minutes. The steward can set new criteria.
- **An objection raised while a default-rule resolution is pending** cancels the pending resolution. **Changing criteria** cancels any pending resolution and re-evaluates.
- **Removing the process** of an active question is refused when `process_outcome` is its only criterion (otherwise an active question would have no criteria).
- **Who can change criteria**: anyone in inbox/dormant/dropped; only the steward in active/standing.
- **Stewardship**: anyone can take over (except in inbox, where you adopt instead). Returning to the inbox (handover to nobody, dormant → inbox, dropped → inbox) clears the steward. Reopening keeps the steward, and makes the actor steward if there's none.
- **Display names**: compared case-insensitively. `system` and `operator` are reserved. Max 60 characters, sent URI-encoded in `X-Actor-Name`.
- **Dormancy** is checked hourly. The effect is the same as a daily job.
- **Duplicate hints**: word overlap with en/fr/es/de stop-words plus substring matching. Spaces are small, so in-memory search is enough.
- **Manual tools** get an optional "link to results" (`extra.results_url`), which covers the Polis report link.
- **GitLab self-hosted instances** are only fetched when the operator lists their host in `GITLAB_HOSTS` (an SSRF guard). Otherwise the URL is treated as unmatched.
- **Markdown** (charter, synthesis) is rendered by a small built-in renderer that builds DOM nodes and never passes HTML through, instead of a sanitizer library.
- **Security extras**: tokens are 256-bit and stored as SHA-256 hashes (their high entropy makes a slow KDF unnecessary), compared with `timingSafeEqual`. Writes are rate-limited (120/min per token, in memory). Cross-origin writes are refused by an `Origin` check. Request logs redact tokens.
- **Date criteria** are entered in the browser's local time and stored in UTC.

## Simplification pass (post-v0)

- **No voting/proposals in the UI for now.** Adding (and enabling/disabling) a tool is a direct form action by anyone with edit access (`POST tools`, `POST tools/:id/enabled`), logged in the activity log. (The Rules-question code was later removed with the rest of the decision model, see below.)
- **"Pool" replaces "Inbox"** in all user-facing text. The internal status id stays `inbox`, so no data migration.
- **"Related" replaces "part of"** in the UI. The data model is unchanged (`parent_id`, one per question).
- **Relations table replaces `parent_id`.** Relations are many-to-many and directed (`from → to`, with a `kind`), so asymmetric kinds ("depends on", "part of"…) can come later; every relation is shown on both questions. Kinds: `related`, and since migration 3 `duplicate`. Migration 2 moves existing `parent_id` links into it (child → parent) and blanks the column. Export format bumped to v2. Relating an existing question is done from its "Related questions" box: suggestions there are link targets, not navigation.
- **Manual tools are editable** (name, URL patterns, states) via `PATCH tools/:id`, logged as `tool.edited`. Automatic tools (GitHub, GitLab) are tied to their adapter and can only be enabled/disabled. Processes keep their tool and recorded state when a tool changes.

## Status model (migration 3)

- **Question-level decisions are removed.** No adopt, resolution criteria, objection windows, stewards, active cap, dormancy, confirm/synthesis or Rules proposals. They may come back for some kinds of questions or processes, deliberately. The code was deleted rather than hidden; the history stays readable in the activity log.
- **One shared vocabulary.** Questions and processes use the same six categories: `not_started`, `open` ("In progress"), `accepted`, `rejected`, `concluded`, `withdrawn` (`unknown` is process-only). Tool states map onto them (`docs/TOOLS.md`).
- **A question follows its process or is set by hand.** `status_source: "process"` copies the process' category on every change (logged as `system` for fetched changes). `"manual"` uses a label from the space's **status labels** (`settings.status_labels`, `[{label, state}]`, editable on the Rules page; at least one `not_started` label, used for new questions). Linking a process makes the question follow it; removing it keeps the status, now set by hand. An `unknown` process state leaves the question unchanged.
- **Migration of old statuses**: with a process (and not resolved/dropped) → follow the process; inbox/dormant → Not started; active/standing → Being discussed (open); resolved → its recorded outcome (default concluded); dropped → Dropped (withdrawn). `duplicate_of_id` → a `duplicate` relation. The objections table is dropped. A `model.simplified` event is logged per space, and the database is snapshotted first (`VACUUM INTO <db>.before-v3.bak`). Tables with changed CHECK constraints are rebuilt (SQLite's 12-step procedure, foreign keys off during migrations).
- **Lanes**: Current (not started + in progress), Ended (accepted, rejected, concluded), Withdrawn. Lists sort by latest activity: the question's own, or its process' activity on the platform (`fetched.dates.updated_at`), whichever is later. Presets: no process, quiet for 30+ days, fetch problems.

## Processes

- **One process per question**, as before, but it can be a **custom process** (`tool_id: "custom"`, not a row in the tool list): a kind in the group's words ("General assembly"), optional title, date and link (any https URL). Its state is set by hand with the space's status labels.
- **Hand-set states by anyone with edit access** (no steward any more).
- **New adapters**: Loomio (public polls and threads via the API Loomio's web client uses, `/api/v1/polls/:key` and `/api/v1/discussions/:key`), Polis (`/api/v3/conversations`, `/api/v3/reports`), Metaculus (`/api/posts/:id/`, only with `METACULUS_TOKEN`; untested live). Verified live in October 2026 except Metaculus. Existing Loomio/Polis seed tools and their processes were switched to automatic by migration 3.
- **Fallback to updating by hand.** Adapters raise `manualFallback` for items that exist but can't be read (401/403, missing token). On attach the process is stored as manual with the reason; on refresh it switches to manual and logs `process.now_manual`. Tools whose adapter isn't usable on this server (Metaculus without a token) behave as manual; the API marks them `auto_unavailable`.
- **Loomio outcome**: closed polls are `concluded` unless the poll template defines a pass test (`results[].test_result`), since Loomio has no general "passed" flag. The facilitator's outcome statement, or the per-option results, become the summary.
- **Last activity**: GitHub/GitLab `updated_at`, Loomio thread `last_activity_at`, Polis `modified` (last vote, in µs). Metaculus has none.
- **Title pre-fill for manual tools** fetches the page and reads `og:title`/`twitter:title`/`<title>` (`src/pagetitle.ts`). Guarded against SSRF: https, port 443, public addresses only (DNS resolved and checked at every redirect hop, redirects followed by hand), 512 KB, 8 s. Generic titles (site name, login walls, bot challenges) are discarded. Kialo and Metaculus pages give nothing useful (login wall / bot challenge).

## Duplicates and removal (migration 4)

- **No duplicate titles or links.** Titles are compared without case, accents, punctuation or spacing (`normalizeTitle`). Links are compared by canonical URL (no `www.`, `#fragment`, trailing slash or `utm_*`) and, when an adapter parses them, by the platform's ids (so `/p/KEY/one-slug` and `/p/KEY/other-slug` are the same Loomio poll). Refused with 409 `duplicate_title` / `duplicate_link` and `details.existing`; the composer shows the existing question (and on a question page, offers to relate it). `resolve-url` reports `existing` before fetching anything. Custom processes aren't checked, since one meeting can address several questions. Near-duplicates (different wording) are still left to the suggestions and the `duplicate` relation.
- **Removing is hiding.** `removed_at` on the question: hidden from lists, counts, suggestions, relations and duplicate checks; its process is no longer refreshed; read-only until restored (`POST …/restore`, refused if its title or link was taken meanwhile). Hard deletion stays impossible (trigger), so the append-only log keeps making sense. Removal is for mistakes and spam; *Withdrawn* is for questions that didn't run their course.
- **State mappings are edited as rows** (the tool's own word → category), for tools and for status labels, instead of `label → state` text lines.

## Civic tech platforms (migration 5)

- **Decidim on any host, without setup.** A seed tool with host-wildcard patterns on Decidim's distinctive paths (`/<space>/<slug>/f/<component>/<proposals|debates|meetings>/<id>`, and `/processes/<slug>`); migration 5 adds it to existing spaces. The adapter POSTs a GraphQL query to the instance's `/api`.
- **Consul per instance.** Consul paths are too generic to match on any host, so a space adds its instance (`POST tools {kind: "consul", base_url}`); patterns are generated for that host. GraphQL GET at `/graphql` with a browser-like user agent (Consul's docs say some servers require it).
- **Fetching arbitrary hosts safely.** Both adapters refuse hosts that don't resolve only to public addresses (same check as title pre-fill), never follow redirects to another host, use fixed paths and small responses. This is a deliberate widening from "fixed API hosts" to "any public host matching the tool's patterns"; DNS rebinding between the check and the request remains a theoretical gap.
- **Version tolerance.** `tolerantQuery` drops fields reported as `undefinedField` and retries (Decidim 0.27 has no `proposalState`; forks differ). Consul tries snake_case when camelCase yields only id/title.
- **Mappings.** Decidim custom proposal states have no known meaning: Concluded once answered, In progress before. Meetings and processes follow their dates (processes end at the end of their end day, UTC). Consul proposals are In progress until retired; the retirement reason gives the category.
- **Drag and drop a link**: dropping a link anywhere (edit link only) fills the home composer; on a question without a process it opens "Link a process" prefilled. Drops into text fields behave normally.

## Tool descriptions and usage (migration 6)

- **"What is it useful for?"** is an optional plain-text `description` on each tool (max 400 characters). Built-in tools ship with one (`SEED_TOOLS`); Consul instances get a default from `INSTANCE_KINDS`. Migration 6 adds the column and fills it for the built-in tools still tied to their adapter, and for Consul instances. Plain text rather than Markdown: it's a one-liner shown in tables and hints.
- **Every tool is editable now, within limits.** Automatic tools (with an adapter) can change their name and description only; their patterns and states belong to the adapter (sending them unchanged is accepted, changing them is refused). Logged as `tool.edited` with before/after.
- **Usage counts** are computed on read (no stored counter): questions per tool, excluding removed ones, and how many of those processes are in progress (process state `open`). Custom processes are counted by kind (`item_type`, case-sensitive), returned as `custom_kinds` and reused as suggestions in the custom-process form and the item-type filter.
- **Hints when linking a process**: the enabled tools' names, folded (`<details>`) with their descriptions, rather than a long always-open list.

## Question dates and timeline (migration 7)

- **One start and one end per question**, instead of dates scattered over the process ("when" on custom processes, opened/closes/ended in the process details, hand-set started/ended). Each date has a source, like the status: `process` (default; what the linked process gives), `manual` (typed) or `none` (explicitly no date, even if the process has one). The process' own dates stay in `fetched.dates` as fetched; the question's dates are derived from them on read (`effectiveDates`).
- **From the process**: start = `opens_at`; end = `resolved_at`, else `closes_at`. One End field covers both "ended" and "will close": an end in the future is a planned end, typed or fetched.
- **Whole days**: a typed date without a time is stored as `"YYYY-MM-DD"`, a calendar day without a time zone, and means the whole day (local midnight to midnight when drawn). With a time, it's stored as a UTC moment. The end-before-start check treats a day as 00:00–23:59 UTC; it only runs when at least one of the two dates is typed (two fetched dates are the platform's business).
- **No guessed dates**: a question without a start date (typed or fetched) isn't drawn; the page says how many were left out. An ended question with a start but no end gets a short fading "end unknown" mark rather than a made-up end. (An earlier version fell back to the creation date and the status-change time; it looked precise but wasn't.)
- **Migration 7** adds the four columns, moves dates typed on processes updated by hand (`fetch_mode = 'manual'`: a custom process' "when", hand-set start/end) to the question as typed dates, and drops `processes.framing`.
- **Process framing removed**: it overlapped with "why it matters" and confused people. The column is dropped; past values remain in the activity log (`process.attached`, `process.framing_changed`). Export format bumped to v4 (fields removed).
- **Timeline drawing**: computed on the server (`GET timeline`, `src/timeline.ts`) with the list's filters (`search.list`), sorted by start; lane defaults to "All". Plain DOM, bars positioned through the CSSOM (`el.style.left/width`), which the strict CSP allows (it forbids inline `style` attributes only). Solid up to today, dashed beyond (planned), dashed outline for something entirely in the future. Ticks are weeks, months or years depending on the span, thinned to about 12 labels. Each bar has a sentence as `aria-label`/tooltip.

## Retrieved or typed, per field (migration 8)

- **One rule for every field.** Title, kind, status, summary, results link, start and end are each *retrieved* (from the linked item, through a tool on the tool list) or *typed*. This replaces three separate mechanisms: "status follows the process / set by hand", hand-set process states ("Update state…"), and the per-date sources of migration 7. Only the link (and "why it matters") is always typed.
- **Per field rather than a whole-item switch**, so a group can keep a PR's status retrieved while typing its own title. To keep it legible, every value carries a tag: `retrieved`, `retrieved as “merged”` (when the platform's word was mapped onto a category) or `typed` (who and when on hover). While a typed value is in use, the retrieved one stays visible under it with "↺ use retrieved". Generic keywords were preferred over naming the tool or the person in the tag (less noise; the details are one hover away).
- **Editing**: double-click a value, or ✎ (for touch screens and keyboards). The editor starts from the current value, retrieved or typed. Clearing a field the item can give stores "none" (a typed `null`); clearing one it can't give just removes the typed value.
- **Storage**: typed values in `questions.typed_json` (`{field: {value, by, at}}`); a field not in there is retrieved. The effective title and status stay in columns (search, counts, duplicate checks) and are recomputed by `fields.sync` after every typed change and refresh; retrieval-driven changes are logged as `system`. `process.fetched` now only holds retrieved data. Views (`fields`) are computed on read and returned by the API and the export.
- **Retrieved only through tools on the list.** Automatic tools give everything their platform exposes; tools updated by hand give the kind (from their URL pattern) and the page title; items that can't be read (private, missing token) the same. Links to sites not on the list are now **accepted** (no longer refused): nothing is retrieved, and the process box offers to add the tool. Adding or editing a tool makes those links join it (`process.tool_matched`), and automatic ones are fetched at once. Duplicate-link checks still only concern items tracked through listed tools: a page that isn't (meeting notes) can serve several questions.
- **Title retrieved by default.** With a link, the title follows the item unless someone gives a different one (at creation, the composer sends the prefilled title; rewriting it makes it typed). Retrieved title changes aren't checked against duplicates; typed ones and "use retrieved" are.
- **What can't be retrieved is typed, never empty.** Title and status always have a value: without a process, or with an item that can't give them, they're typed (by the creator, or kept as they were when a process is removed or an item becomes private). Linking an item that can give a status makes the status follow it; the typed kind, summary and results link of a replaced process are dropped (they described it), typed dates are kept.
- **Tools lose their own state words** (`state_map`, migration 8 drops the column). A typed status always uses the space's status labels, the same everywhere; the platform's own word only appears for retrieved statuses ("retrieved as …").
- **Migration 8** turns sources into typed values: a title is typed unless it's exactly the item's retrieved title; statuses set by hand, or following a process updated by hand, become typed (the hand-set word becomes the label); a custom process' kind, and summaries and results links set by hand, move from the process to the question; typed and "none" dates carry over. The export format goes to v5.

- **Item page and creation tweaks.** The "Process" section is called **Attached link** on a question's page. "Why it matters" is no longer shown or asked for (the summary covers it; the column and `why_it_matters` in the API and export stay, so nothing is lost, and old values are still searched). The Edit and Remove… buttons are gone from the page: title and fields are edited in place; removal remains in the API (`POST questions/:id/remove`) and restoring in Rules. *Results* (`results_url`, key unchanged) accepts plain text as well as a link; only https links are rendered as links, and a value that looks like a link but isn't https is refused. The composer shows the optional **Details** (kind, status, summary, results, start, end) as soon as there's a title or link; for a readable link the fields are pre-filled with the retrieved values, and only values the user changes are sent (so typed); unchanged or emptied ones keep following the item. They are sent as `status`, `process.kind` and `fields` on `POST questions`, and typed. A stray "null" after ✎ came from `Element.append(null)` writing the word; field cells now filter empty parts.

## Header tabs and dashboard

- **Tabs are List, Timeline, Rules, Activity.** The lanes (Current, Ended, Withdrawn, plus All) moved from the header to a row of chips above the search, shared by the list and the timeline (replacing the "Lane" filter select). Counts stay on the chips. `#/list` still defaults to the Current lane, and remains the landing page (it holds the composer and the drop target).
- **No tabs; a menu.** The header is the space name (→ the items) and, on the right, the display name and a **Menu** (Dashboard, Tools, Activity, How this works, Export). The menu is a plain button with `aria-expanded` and a `hidden` list, not `<details>` (more predictable across browsers); it closes on a click elsewhere, on Escape or on choosing an item. The page opens on the add bar, placeholder "Name a process or paste its link." (more general than "question"). Pages other than the items have a "← Items" link back. **Rules was split**: `#/rules` (kept as the route) is now **Tools** (tool list, custom kinds, status labels, removed questions); the charter is `#/how`; Export is a menu action (the download panel is gone).
- **List and timeline are one page**, `#/list`, with a two-symbol toggle (CSS-drawn icons; list selected by default; `view=timeline` in the URL, old `#/timeline` links redirect). The toggle keeps the search, lane and filters; the timeline view opens on All when no lane is given. The page isn't named in the UI any more (no tab); "Items" is the working name, "Processes" would be wrong for questions without one.
- **Dashboard puzzle.** Fixed-size cells (4 columns × 168px rows; 2 columns under 860px, 1 under 560px, where heights become automatic); each widget declares `size: [cols, rows]` and `grid-auto-flow: dense` fills gaps left by hidden ones. Removed: Activity grid, Who's active, Monthly goal (and their data: `days`, `people`, `month`). The streak moved into Momentum.
- **Lanes beside the search, shortcuts under Filters.** The chips are Current, Ended, All (no Withdrawn chip: use Filters → Status; old `lane=withdrawn` links still work). The three shortcuts (no process yet, quiet, fetch problems) moved inside Filters, which opens when one is active.
- **The dashboard is `#/dashboard`** (a hash route like the others; `/home` is the public landing page of the server), reached from the menu.
- **Dashboard widgets are prototypes**, built to be tried and pruned: `src/dashboard.ts` computes everything on demand from questions and the activity log (`GET dashboard`, nothing stored), `public/dashboard.js` has one entry per widget (`WIDGETS`, with a one-line "why"). Each person can hide widgets (`localStorage` `qr:dash:hidden`); the monthly goal is also per browser (`qr:dash:goal`). To drop a widget for good: delete its entry in `WIDGETS` (and its part in `dashboard()` if nothing else uses it).
- **"Answered"** = accepted, rejected or concluded. When: the last event moving the question into one of those (a retrieved `question.status_changed`, or a typed status in `question.fields_changed`), else its creation date (it arrived already ended; excluded from "typical time to answer").
- **People** are the actors of the log, minus `system`/`operator`; "Your impact" matches the display name case-insensitively. Names aren't verified, so the leaderboard-style widgets (Who's active, Milestones, streak, goal) are motivational only, not a record. Worth discussing before keeping: ranking can discourage as much as it encourages.

## Relation types: parent/child, related, duplicate

- **Three stored kinds, no migration.** `relations.kind` has no CHECK constraint, so `child_of` joins `related` and `duplicate`. Direction carries the meaning: `from child_of to` (to is the parent), `from duplicate to` (from is the copy). Creating a relation says what *this* question is (`related`, `child_of`, `parent_of`, `duplicate_of`, `duplicated_by`); `parent_of` and `duplicated_by` are stored reversed, so each fact has one form. `duplicate` is still accepted as `duplicate_of`. Pairs that were migrated from the old `parent_id` stay `related` (indistinguishable from other related links); unlink and relink to make them parent/child.
- **One relation per pair** (unchanged): linking two questions that are related in any way is refused (`already_related`), so a pair is never both related and parent/child.
- **Several parents allowed, loops refused.** The hierarchy is a DAG: a topic can belong under two umbrellas. `child_of` links must never close a loop; creating one that would returns 409 `hierarchy_loop` with the chain (“C” → “B” → “A”). The check covers removed questions too (restoring one would otherwise bring the loop back). Duplicate and related links aren't part of it. Logic in `src/relations.ts`.
- **Hierarchy in the list and timeline (`hierarchy=1`).** Arranged on the server (`arrange`), same function for both. With several parents a question stands once, under the parent of its oldest link that is in the list; other parents are mentioned on its card ("Child of …"). When no parent is in the list (another lane, a search), the child is at the top and its card says "Child of …". The UI asks for it by default; Filters → Children → Listed apart (`flat=1`) turns it off, and the API stays flat unless asked. Siblings keep the list's order (activity, creation) or the timeline's (start date); a parent's children are not re-sorted by their own parent's dates.
- **Every kind is drawn, none is just written.** Children are nested lists with a line down the side and a tick per card (CSS only). A **duplicate** nests the same way under its original (dashed tick, "≡ duplicate" tag): it is directional, and subordinate to the original anyway; the cost is that it stands there rather than in its own sort position. If a question is both a child and a duplicate, the parent wins; candidates that would close a loop are skipped (duplicate links aren't loop-checked, `arrange` just never nests under a descendant). **Related** is symmetric, so no nesting: in the list, related questions at the same level (the same siblings) are moved next to each other, as a group at the position of its first member, with a dotted line across the gap. A group follows related links through each other (A–B, B–C → A, B, C); a long chain makes a long group, accepted since related links are rare. Related questions at different levels aren't joined and stay written on the card. The timeline doesn't regroup (its order is the date): duplicates nest there with a "≡" mark, related ones aren't drawn. What the layout shows is left off the card's muted text; what it can't (other level, filtered out, flat list) stays written ("Related to A", "Child of B"…).
- **Item page**: every linked question with its type (Parent, Child, Related, This is a duplicate of, Duplicated by), parents first. The API gives each one a `role` (what the other question is to this one) so clients don't reason about `from`/`to`; lists carry the same `links` for each question.
- **Duplicates suggest withdrawing, never force it.** When a question is marked as a duplicate, its page says so and offers one click to withdraw it (a typed status, with a note "Duplicate of …" in the log). The question page of the original offers to withdraw its not-yet-withdrawn duplicates. Nothing changes without the click: duplicates are sometimes kept (a different framing, a different process).
- **Not done**: changing a relation's type in place (unlink, then relink), collapsing a branch, connector lines between far-apart related cards (needs an overlay), ancestors breadcrumb on the item page, hierarchy-aware lanes (a child isn't pulled into a lane because its parent is there).
